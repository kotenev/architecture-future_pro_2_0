# Расширенный технический радар "Будущее 2.0"

## 1. Описание

Технический радар описывает текущий и целевой технологический ландшафт компании "Будущее 2.0" в горизонте трёх лет. Радар включает технологии, инструменты и архитектурные паттерны, классифицированные по четырём статусам:

| Статус | Описание                                                                          |
|--------|-----------------------------------------------------------------------------------|
| Adopt  | Рекомендовано к активному использованию во всех новых проектах                    |
| Trial  | Проверяется в пилотных проектах, допустимо в production с ограничениями           |
| Assess | Изучается и оценивается, используется только в PoC                                |
| Hold   | Не рекомендуется для новых проектов; существующее использование подлежит миграции |

## 2. Архитектурные паттерны и подходы

| Паттерн / Подход                                  | Статус | Обоснование                                                                                                                                                                           |
|---------------------------------------------------|--------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Data Mesh                                         | Adopt  | Ключевой паттерн целевой архитектуры. Каждый домен (финтех, клиники, ИИ, головной офис) владеет своими данными как продуктом. Позволяет масштабировать аналитику без монолитного DWH. |
| Event-Driven Architecture (EDA)                   | Adopt  | Целевая модель интеграции между доменами. Заменяет синхронные вызовы через Apache Camel на асинхронные доменные события, обеспечивая слабую связанность.                              |
| Self-service BI / Data Portal                     | Adopt  | Портал самообслуживания - одна из двух ключевых задач руководства. Бизнес-пользователи конструируют отчёты в рамках своего уровня доступа.                                            |
| Domain-Driven Design (DDD)                        | Adopt  | Фундамент для выделения bounded contexts и определения границ доменов. Обеспечивает чёткое разделение ответственности.                                                                |
| CQRS (Command Query Responsibility Segregation)   | Trial  | Применяется в доменах с высокой нагрузкой на чтение (аналитические витрины) при сохранении транзакционной записи. Пилотируется в финтех-домене.                                       |
| Event Sourcing                                    | Assess | Оценивается для финансового домена, где критична полная история изменений состояний (кредиты, счета). Требует зрелости команды.                                                       |
| Medallion Architecture (Bronze -> Silver -> Gold) | Adopt  | Стандарт организации слоёв данных в Data Lakehouse. Bronze - сырые данные, Silver - очищенные, Gold - бизнес-витрины.                                                                 |
| Anti-Corruption Layer (ACL)                       | Adopt  | Обязателен для интеграций с легаси-системами (DWH SQL Server, Apache Camel) на этапе миграции. Изолирует новые сервисы от устаревших моделей данных.                                  |
| Strangler Fig Pattern                             | Trial  | Используется для постепенного вывода бизнес-логики из DWH SQL Server 2008 в доменные сервисы без big-bang миграции.                                                                   |
| Data as a Product                                 | Adopt  | Каждый домен публикует дата-продукты с SLA, документацией и контрактами (schema registry). Основа Data Mesh.                                                                          |
| Federated Computational Governance                | Trial  | Модель управления данными, при которой единые стандарты задаются централизованно, но реализуются доменными командами автономно.                                                       |
| Zero Trust Security                               | Trial  | Модель безопасности для облачной инфраструктуры с медицинскими и финансовыми данными. Каждый запрос аутентифицируется и авторизуется.                                                 |

## 3. Платформы данных и хранения

| Технология                                               | Статус | Обоснование                                                                                                                                                              |
|----------------------------------------------------------|--------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Apache Kafka                                             | Adopt  | Основа событийной шины. Обеспечивает потоковую передачу доменных событий, гарантии доставки (at-least-once), поддержку DLQ. Заменяет Apache Camel на критическом пути.   |
| Apache Kafka Connect                                     | Adopt  | CDC (Change Data Capture) из легаси DWH и баз данных доменов в Kafka-топики. Ключевой компонент миграции.                                                                |
| Confluent Schema Registry                                | Adopt  | Каталог схем для контрактов доменных событий. Обеспечивает совместимость версий (Avro/Protobuf).                                                                         |
| Apache Spark                                             | Adopt  | Основной движок для batch- и micro-batch-обработки данных в Data Lakehouse. Трансформации Bronze -> Silver -> Gold.                                                      |
| Apache Flink                                             | Trial  | Near-real-time обработка потоков данных. Пилотируется для потоковых витрин (финтех-транзакции, мониторинг пациентского потока).                                          |
| Delta Lake / Apache Iceberg                              | Adopt  | Табличный формат для Data Lakehouse с поддержкой ACID, time travel и schema evolution. Delta Lake - основной выбор (зрелая экосистема Spark).                            |
| S3-совместимое хранилище (Yandex Object Storage / MinIO) | Adopt  | Объектное хранилище для Data Lakehouse. Основа для слоёв Bronze/Silver/Gold. Масштабируемое, экономически эффективное.                                                   |
| PostgreSQL                                               | Adopt  | OLTP-база для доменных сервисов. Заменяет SQL Server для новых микросервисов.                                                                                            |
| ClickHouse                                               | Trial  | Колоночная OLAP-БД для быстрых аналитических запросов в витринах данных. Пилотируется как альтернатива Gold-слою для интерактивных дашбордов.                            |
| Microsoft SQL Server 2008                                | Hold   | Текущий DWH. Критически устаревший (end of support). Подлежит постепенной миграции через Strangler Fig и CDC. На переходном этапе используется как «мост совместимости». |
| Redis                                                    | Adopt  | Кэширование горячих данных, сессий, результатов частых запросов в портале самообслуживания.                                                                              |
| MongoDB                                                  | Assess | Оценивается для хранения полуструктурированных медицинских данных (результаты ИИ-моделей, метаданные исследований).                                                      |

## 4. Аналитика и визуализация

| Технология             | Статус | Обоснование                                                                                                                                                                |
|------------------------|--------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Apache Superset        | Adopt  | Основа портала самообслуживания (Self-service BI). Open-source, поддерживает SQL-запросы, кастомные дашборды, ролевую модель доступа. Заменяет кастомизированный Power BI. |
| dbt (Data Build Tool)  | Adopt  | Трансформации и моделирование данных в слоях Silver -> Gold. Документация моделей, тестирование качества данных, lineage.                                                  |
| DataHub / Apache Atlas | Trial  | Каталог данных и метаданных. Обеспечивает discoverability дата-продуктов, lineage, governance. Пилотируется DataHub.                                                       |
| Great Expectations     | Trial  | Фреймворк проверки качества данных. Data contracts между доменами. Валидация на границах Bronze/Silver/Gold.                                                               |
| Power BI               | Hold   | Текущая BI-система с тяжёлыми кастомизациями поверх DWH. Подлежит замене на Apache Superset по мере миграции витрин. Сохраняется временно для legacy-отчётов.              |
| PowerBuilder           | Hold   | Клиентский интерфейс операторов клиник. Устаревший стек, подлежит замене на современный веб-интерфейс (React/Vue).                                                         |

## 5. Интеграция и API

| Технология                              | Статус | Обоснование                                                                                                                                                         |
|-----------------------------------------|--------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Apache Kafka (как интеграционная шина)  | Adopt  | Замена Apache Camel на событийном пути. Асинхронная интеграция между доменами.                                                                                      |
| REST API (OpenAPI 3.x)                  | Adopt  | Стандарт синхронных API для доменных сервисов. Документированные контракты.                                                                                         |
| gRPC                                    | Trial  | Высокопроизводительное межсервисное взаимодействие внутри доменов (финтех, ИИ-сервисы).                                                                             |
| GraphQL                                 | Assess | Оценивается для портала самообслуживания: гибкие запросы к витринам данных без необходимости множества REST-эндпоинтов.                                             |
| Apache Camel                            | Hold   | Текущая интеграционная шина. Сохраняется как «мост совместимости» на этапе миграции (этап 2), затем выводится. ACL-слой изолирует новые сервисы от маршрутов Camel. |
| API Gateway (Kong / Yandex API Gateway) | Adopt  | Единая точка входа для API доменов. Rate limiting, аутентификация, маршрутизация, мониторинг.                                                                       |

## 9. Принципы принятия технологических решений

1. Open-source first: приоритет открытым технологиям для снижения лицензионных затрат и vendor lock-in.
2. Cloud-native: все новые сервисы проектируются для облака (контейнеры, managed-сервисы, IaC).
3. Domain ownership: каждый домен выбирает инструменты в рамках стандартов платформы (Federated Governance).
4. Security by design: безопасность встроена в архитектуру, а не добавлена поверх (Zero Trust, encryption, RBAC).
5. Data contracts: все межсервисные и межсменные интеграции описаны формальными контрактами (Schema Registry, OpenAPI, AsyncAPI).
