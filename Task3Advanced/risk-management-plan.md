# План управления рисками трансформации "Будущее 2.0"

## 1. Стратегия управления рисками

Для каждого риска определена одна из четырёх стратегий реагирования:

- Mitigation (снижение): активные меры для уменьшения вероятности или влияния.
- Avoidance (избежание): изменение плана для полного исключения риска.
- Transfer (передача): перенос ответственности на третью сторону.
- Acceptance (принятие): осознанное принятие с мониторингом.


## 2. Детальный план мер по каждому риску

### R01 - сложность миграции данных из DWH

| Параметр      | Значение                                   |
|---------------|--------------------------------------------|
| Стратегия     | Mitigation                                 |
| Тип мер       | Технические и управленческие               |
| Ответственный | Data Migration Lead и Enterprise Architect |

Технические меры:

1. Инкрементальная миграция через CDC (Debezium). Вместо единоразового переноса данных настроить Change Data Capture из MS SQL Server. Данные будут поступать в Kafka и далее в Data Lake (Iceberg) в режиме near-real-time. Это позволяет мигрировать без остановки DWH.

2. Фаза dual-write / dual-read. На переходном этапе каждый домен читает данные параллельно из DWH и Data Lake. Автоматизированная сверка (reconciliation) обнаруживает расхождения. Только после успешной верификации домен переключается на новый источник.

3. Каталогизация бизнес-логики DWH. Инструментами типа SQL Server Profiler и ApexSQL Analyze выявить все активные хранимые процедуры, триггеры и views. Классифицировать по критичности. Некритичные трансформации реализовать в dbt.

Управленческие меры:

4. Пилотная миграция одного домена (финансовый). Начать с наименее рискованного набора данных. Зафиксировать метрики: время, расхождения, обратные откаты. Использовать результаты для планирования остальных доменов.

5. Rollback-стратегия. Для каждого этапа миграции определить критерии go/no-go и сценарий отката. DWH не выводить из эксплуатации до полной верификации целевого состояния.

KPI мониторинга: Процент мигрированных доменов; количество расхождений при reconciliation; время отката.


### R02 - несовместимость схем данных при переходе на Event-Driven

| Параметр      | Значение                         |
|---------------|----------------------------------|
| Стратегия     | Mitigation                       |
| Тип мер       | Технические                      |
| Ответственный | Domain Architect и Data Engineer |

Технические меры:

1. Schema Registry с backward compatibility. Confluent Schema Registry с политикой BACKWARD_TRANSITIVE. Каждое изменение контракта проходит проверку на совместимость с предыдущими версиями.

2. Canonical Data Model на уровне платформы. Определить shared kernel - минимальный набор общих типов данных (пациент, договор, транзакция) с чёткими контрактами в Protobuf. Домены публикуют события, маппящиеся на этот канонический формат.

3. Contract testing в CI/CD. В пайплайне каждого домена запускать автоматические тесты совместимости: producer-контракт -> Schema Registry -> consumer-контракты всех подписчиков.

4. Event Versioning Strategy. Использовать стратегию "новое событие и deprecated старое": при кардинальных изменениях публиковать новую версию события (v2) параллельно со старой на протяжении transition window (2-4 недели).

KPI мониторинга: Количество schema violations в Schema Registry; время на адаптацию потребителей к новой схеме.


### R03 - degradation производительности в переходный период

| Параметр      | Значение                |
|---------------|-------------------------|
| Стратегия     | Acceptance и Mitigation |
| Тип мер       | Технические             |
| Ответственный | Platform Engineer и SRE |

Технические меры:

1. Раздельные ресурсные пулы. В Kubernetes выделить отдельные node pools и resource quotas для легаси-мостов (DWH Bridge, Camel ACL) и целевых сервисов. Нагрузка легаси не влияет на целевую платформу.

2. Кэширование отчётности. Для Self-Service BI Portal внедрить Redis-кэш результатов часто запрашиваемых запросов. Materialized views в ClickHouse для предварительно агрегированных данных.

3. Performance budget. Установить SLA: формирование стандартного отчёта <= 30 сек, дашборд <= 5 сек. Мониторить через Prometheus и Grafana. При превышении - автоматический алерт.

Управленческие меры:

4. Коммуникация с бизнесом. Прозрачно информировать бизнес-пользователей о временном снижении производительности на этапе миграции. Предоставить timeline улучшения.


### R04 - vendor lock-in на облачного провайдера

| Параметр      | Значение             |
|---------------|----------------------|
| Стратегия     | Mitigation           |
| Тип мер       | Технические          |
| Ответственный | Enterprise Architect |

Технические меры:

1. Abstractions layer. Использовать cloud-agnostic технологии: Kubernetes (вместо cloud-specific container services), Apache Kafka (вместо managed messaging), Terraform (IaC абстракция провайдера).

2. S3-compatible API. Data Lake строить на S3-compatible API и Apache Iceberg (open table format). Iceberg работает на любом S3-совместимом хранилище.

3. Минимизация managed-зависимостей. Managed PostgreSQL и Managed Kafka допустимы, но connection logic абстрагировать через environment variables и Terraform modules.

KPI мониторинга: Процент компонентов с vendor-specific API; время оценки миграции на альтернативного провайдера.


### R05 - нарушение data consistency между доменами

| Параметр      | Значение                        |
|---------------|---------------------------------|
| Стратегия     | Mitigation                      |
| Тип мер       | Технические                     |
| Ответственный | Domain Architect и Fintech Lead |

Технические меры:

1. Saga-паттерн для критичных операций. Для финансовых транзакций (кредиты, платежи) использовать Orchestration-based Saga с компенсирующими транзакциями. Координатор на базе Temporal / Cadence.

2. Outbox Pattern. Запись события и обновление бизнес-данных в одной транзакции БД. Debezium читает outbox-таблицу и публикует в Kafka. Гарантия at-least-once delivery.

3. Idempotent consumers. Все потребители событий реализуют идемпотентность через deduplication key (event_id). Это защищает от дублирования при retry.

4. Reconciliation service. Ежедневная автоматическая сверка ключевых финансовых агрегатов между доменом финтех и Data Lake. Алерт при расхождении > порога.

KPI мониторинга: количество компенсирующих транзакций в месяц; результаты daily reconciliation.


### R06 - дефицит компетенций по целевому стеку

| Параметр      | Значение       |
|---------------|----------------|
| Стратегия     | Mitigation     |
| Тип мер       | Управленческие |
| Ответственный | CTO и HR       |

Управленческие меры:

1. Программа обучения. Поэтапное обучение команд: (1) Kafka и Event-Driven 1–2 месяца; (2) Kubernetes и CI/CD 2-4 месяца; (3) Data Mesh + dbt + Flink 4-6 месяца. Формат: внутренние воркшопы + онлайн-курсы + хакатоны.

2. Embedded experts. Привлечь 2-3 внешних экспертов (Kafka, Kubernetes, Data Engineering) на 6-12 месяцев в формате embedded consulting. Они работают внутри команд и передают знания через pair programming.

3. Community of Practice. Создать внутренние гильдии: Data Engineering Guild, Platform Engineering Guild. Еженедельные tech talks, sharing sessions, post-mortem reviews.

4. Внутренний Tech Radar. Вести и обновлять технический радар компании (см. Задание 5), используя его как инструмент для приоритизации обучения.

KPI мониторинга: количество сертифицированных специалистов; покрытие доменов компетенциями; time-to-hire для целевых ролей.


### R07 - сопротивление изменениям

| Параметр      | Значение                            |
|---------------|-------------------------------------|
| Стратегия     | Mitigation                          |
| Тип мер       | Управленческие                      |
| Ответственный | Change Manager и Data Product Owner |

Управленческие меры:

1. Early wins. В первые 3 месяца реализовать один показательный отчёт в Self-Service BI, который был недоступен или очень медленно строился в текущей системе. Продемонстрировать бизнесу конкретный выигрыш.

2. Data Champions. В каждом бизнес-подразделении выделить 1–2 data-амбассадора из числа лояльных к изменениям сотрудников. Они обучаются первыми и помогают коллегам.

3. Параллельная работа BI. Не отключать Power BI до момента, пока больше 80% пользователей не перейдут на новый портал добровольно. Мягкая миграция вместо hard cutoff.

4. Feedback loop. Ежемесячные demo-сессии с бизнес-пользователями. Собирать обратную связь, приоритизировать фичи нового BI по запросам.


### R08 - конфликт приоритетов между доменами

| Параметр      | Значение                   |
|---------------|----------------------------|
| Стратегия     | Mitigation                 |
| Тип мер       | Управленческие             |
| Ответственный | Enterprise Architect и CTO |

Управленческие меры:

1. Architecture Governance Board. Создать архитектурный комитет с представителями всех четырёх подразделений. Еженедельные стендапы, ежемесячные ревью приоритетов.

2. WSJF-приоритизация. Использовать Weighted Shortest Job First для ранжирования проектов трансформации. Объективные метрики вместо политического лоббирования.

3. Shared platform team. Выделить кросс-доменную Platform Team, которая развивает общую инфраструктуру (Kafka, K8s, observability) независимо от доменных приоритетов.

4. Чёткие SLA между доменами. Оформить Inter-Domain SLA: гарантированные latency, availability, throughput на границах доменов.


### R09 - потеря ключевых специалистов по легаси

| Параметр      | Значение                     |
|---------------|------------------------------|
| Стратегия     | Mitigation и Transfer        |
| Тип мер       | Управленческие и технические |
| Ответственный | CTO + HR + Domain Leads      |

Управленческие меры:

1. Retention program. Финансовая мотивация для ключевых экспертов по DWH и PowerBuilder: бонус за каждый успешно мигрированный домен. Удержание до завершения миграции.

2. Knowledge harvesting. Систематическое документирование знаний: ADR-сессии, видеозаписи разборов бизнес-логики, wiki с описанием хранимых процедур. Дедлайн: завершить до конца 1-го этапа.

3. Cross-training. Каждый легаси-эксперт работает в паре с инженером целевой платформы. Bus factor >= 2 для каждой критичной области знаний.

Технические меры:

4. Автоматический reverse engineering. С помощью инструментов (SchemaSpy, SQL Server Data Tools) автоматически сгенерировать документацию по структуре DWH: ERD-диаграммы, dependency graphs, описания хранимых процедур.

KPI мониторинга: bus factor по каждому легаси-компоненту; процент задокументированной бизнес-логики; retention rate ключевых специалистов.


### R10 - отказоустойчивость Kafka-кластера

| Параметр      | Значение                |
|---------------|-------------------------|
| Стратегия     | Mitigation              |
| Тип мер       | Технические             |
| Ответственный | Platform Engineer / SRE |

Технические меры:

1. Multi-AZ deployment. Kafka-брокеры распределены по >= 3 зонам доступности. Replication factor >= 3, min.insync.replicas = 2.

2. MirrorMaker 2 для DR. Асинхронная репликация в DR-регион. RPO < 5 мин, RTO < 30 мин.

3. Circuit breaker на producer-стороне. При недоступности Kafka продюсеры используют локальный буфер (disk-based queue) и retry с exponential backoff.

4. Мониторинг и алертинг. Under-replicated partitions, consumer lag, disk usage - алерты в PagerDuty/Opsgenie с runbook для каждого сценария.


### R11 - schema evolution и обратная совместимость

| Параметр      | Значение          |
|---------------|-------------------|
| Стратегия     | Mitigation        |
| Тип мер       | Технические       |
| Ответственный | Domain Architects |

Технические меры:

1. Schema Registry с compatibility levels - BACKWARD_TRANSITIVE по-умолчанию. Критичные топики: FULL_TRANSITIVE.

2. Schema governance в CI/CD. Pull request не мёржится без прохождения schema compatibility check.

3. Deprecation policy. Минимум 4 недели transition window при deprecation события. Автоматический мониторинг потребителей deprecated-версий.


### R12 - безопасность данных при миграции

| Параметр      | Значение                     |
|---------------|------------------------------|
| Стратегия     | Mitigation и Transfer        |
| Тип мер       | Технические и управленческие |
| Ответственный | CISO и DPO                   |

Технические меры:

1. Encryption in transit и at rest. TLS 1.3 для всех соединений. AES-256 для хранимых данных. Kafka с SASL_SSL.

2. Токенизация PII. Персональные данные (ФИО, СНИЛС, данные карт) токенизируются при записи в Data Lake. Оригиналы хранятся в изолированном vault.

3. Network isolation. VPC с private subnets для data-компонентов. Доступ только через bastion host и VPN. mTLS между сервисами.

4. Data classification. Автоматическая маркировка данных по уровню конфиденциальности в Data Catalog. Политики доступа на основе классификации.

Управленческие меры:

5. Аудит безопасности. Привлечь внешнего аудитора для penetration testing перед каждым этапом миграции. Сертификация по ГОСТ Р57580.1 для финансового домена.


### R13 - усложнение observability

| Параметр      | Значение      |
|---------------|---------------|
| Стратегия     | Mitigation    |
| Тип мер       | Технические   |
| Ответственный | SRE Team Lead |

Технические меры:

1. Unified observability stack. Prometheus (метрики) + Loki (логи) + Tempo (трейсы) + Grafana (визуализация). OpenTelemetry SDK во всех сервисах.

2. Distributed tracing. Обязательный trace_id + correlation_id через все Kafka-события и HTTP-вызовы. Сквозная трассировка от пользовательского запроса до Data Lake.

3. SLI/SLO framework. Для каждого домена определить Service Level Indicators и Objectives. Error budgets как основа для принятия решений о скорости развития vs стабильности.


### R14 - рост латентности при гео-распределении

| Параметр      | Значение                |
|---------------|-------------------------|
| Стратегия     | Acceptance и Mitigation |
| Тип мер       | Технические             |
| Ответственный | Platform Architect      |

Технические меры:

1. CQRS по регионам. Read-реплики в каждом регионе. Записи маршрутизируются в primary-регион.

2. Edge caching. CDN + региональный Redis для статического контента и часто запрашиваемых данных.

3. Асинхронные операции по умолчанию. Sync-вызовы между регионами - только для критичных финансовых операций с SLA < 500 мс.

## 4. Расписание мониторинга рисков

| Частота       | Активности                                                                                                          |
|---------------|---------------------------------------------------------------------------------------------------------------------|
| Еженедельно   | SRE-обзор метрик Kafka, reconciliation, consumer lag. Стендап Architecture Governance Board.                        |
| Ежемесячно    | Обзор карты рисков: пересмотр вероятностей и влияния. Demo бизнес-пользователям. Отчёт о миграции.                  |
| Ежеквартально | Стратегическая ретроспектива: прогресс трансформации vs roadmap. Пересмотр приоритетов доменов. Аудит безопасности. |
| По событию    | Post-mortem после каждого инцидента. Пересмотр мер при реализации любого риска.                                     |


## 5. Критерии эскалации

| Уровень     | Условие                                            | Действие                                                               |
|-------------|----------------------------------------------------|------------------------------------------------------------------------|
| Норма       | Все KPI в пределах целевых значений                | Стандартный мониторинг                                                 |
| Внимание    | KPI отклоняется > 20% или новый риск выявлен       | Обсуждение на Architecture Governance Board, назначение ответственного |
| Критический | SLA нарушен, данные потеряны, миграция остановлена | Эскалация на CTO/CEO, War Room, пересмотр roadmap                      |
