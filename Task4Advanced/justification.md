# Обоснование событийного подхода - "Будущее 2.0"

## 1. Контекст и проблемы текущей архитектуры

### Текущее состояние (AS-IS)

Компания "Будущее 2.0" сегодня использует централизованную архитектуру, построенную вокруг двух ключевых компонентов:

- DWH (MS SQL Server 2008) - центральное хранилище, в которое заложена значительная часть бизнес-логики. DWH выступает одновременно как база данных, интеграционный хаб и аналитическая платформа.
- Интеграционная шина Apache Camel - обеспечивает point-to-point и маршрутизированные интеграции между DWH, ИИ-сервисами, финтех-сервисами и внутренними системами.

### Ключевые проблемы

| # | Проблема                                                                                                        | Следствие                                                                         | Влияние на бизнес                                                                               |
|---|-----------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| 1 | Монолитный DWH - вся бизнес-логика сконцентрирована в одном SQL Server 2008                                     | Любое изменение требует координации всех команд; нельзя масштабировать независимо | Замедление time-to-market; формирование сложных отчётов занимает часы                           |
| 2 | Тесная связанность через Camel - интеграции реализованы синхронно, маршруты знают о структуре данных друг друга | Каскадные отказы; изменение одного домена ломает другие                           | Сбои в финтех влияют на клинические системы и наоборот                                          |
| 3 | Отсутствие доменной автономии - все данные хранятся в общем DWH                                                 | Команды не могут развивать свои продукты независимо                               | Невозможно подключить новые бизнес-направления (фармакология, электроника) без рефакторинга DWH |
| 4 | Пакетная обработка - аналитика строится через ETL-процессы (batch)                                              | Отчёты актуальны с задержкой от часов до суток                                    | Невозможно реагировать на события в реальном времени (просрочки, критические диагнозы)          |
| 5 | Сотни терабайт в одном хранилище - объём данных растёт, производительность падает                               | Трансформации занимают всё больше времени                                         | Падение производительности аналитических процессов                                              |
| 6 | Legacy-технологии - SQL Server 2008, PowerBuilder                                                               | Отсутствие поддержки вендора, ограниченный пул специалистов                       | Рост технического долга и рисков безопасности                                                   |

## 2. Почему Event-Driven Architecture (EDA)

### 2.1. Стратегическое соответствие целям "Будущего 2.0"

Компания определила долгосрочную цель: через три года архитектура должна представлять собой слабосвязанную событийную платформу, в рамках которой домены взаимодействуют через события и реактивные потоки. EDA - это не просто технический выбор, а стратегическое решение, напрямую вытекающее из бизнес-видения.

### 2.2. Сравнение подходов

| Критерий                  | Текущая архитектура (Camel + DWH)      | Событийная архитектура (EDA)                        |
|---------------------------|----------------------------------------|-----------------------------------------------------|
| Связанность               | Высокая: синхронные вызовы, общая БД   | Низкая: домены общаются через асинхронные события   |
| Масштабирование           | Вертикальное (дороже DWH)              | Горизонтальное (добавляем consumer-ы)               |
| Добавление домена         | Рефакторинг DWH + новые Camel-маршруты | Домен подписывается на нужные топики                |
| Отказоустойчивость        | Каскадные отказы через шину            | Изоляция: падение потребителя не влияет на источник |
| Скорость данных           | Batch (часы/сутки)                     | Near-real-time (секунды/минуты)                     |
| Автономия команд          | Низкая: общий DWH - bottleneck         | Высокая: каждый домен владеет своими данными        |
| Аудит и воспроизводимость | Сложно: данные перезаписываются в DWH  | Встроено: event log = полная история изменений      |
| Эволюция схем             | Ломающие миграции БД                   | Schema Registry + backward-compatible эволюция      |
| Поддержка регуляторов     | Требует отдельных механизмов аудита    | Event Sourcing = нативная аудит-трассировка         |

## 3. Преимущества EDA для "Будущего 2.0"

### 3.1. Гибкость: подключение новых бизнес-направлений

Проблема: компания планирует интегрировать фармацевтические компании и производителя электроники. В текущей архитектуре это потребует модификации DWH и создания новых Camel-маршрутов.

Решение с EDA: новый домен (например, "Фармакология") просто подписывается на релевантные события (PatientRegistered, TreatmentPrescribed) и публикует свои (DrugDispatched, PrescriptionFulfilled). Никаких изменений в существующих доменах.

Преимущества: Time-to-market для подключения нового направления сокращается с месяцев до недель.

### 3.2. Масштабируемость: рост данных и пользователей

Проблема: сотни терабайт в DWH, формирование отчётов занимает часы.

Решение с EDA:
- Каждый домен хранит только свои данные в оптимальном для себя хранилище (PostgreSQL, ClickHouse, MongoDB).
- Аналитический домен (Data Showcase) строит материализованные представления из потока событий, используя stream processing (Kafka Streams / Flink).
- Горизонтальное масштабирование: увеличение нагрузки → добавление partitions и consumer instances.

Выигрыш: формирование отчётов из часов → минуты/секунды.

### 3.3. Скорость реакции: от batch к near-real-time

Проблема: пакетная обработка не позволяет оперативно реагировать на бизнес-события.

Решение с EDA: события обрабатываются в момент возникновения:
- PaymentOverdue -> мгновенный алерт кредитному менеджеру.
- InventoryLow -> автоматический запуск заявки на закупку.
- AIStudyCompleted -> результат ИИ доступен врачу за секунды, а не после ночного ETL.

Выигрыш: скорость принятия бизнес-решений повышается на порядок.

### 3.4. Автономия доменных команд

Проблема: все команды зависят от DBA DWH для любых изменений. Это классический организационный bottleneck.

Решение с EDA + Data Mesh:
- Каждый домен это автономная команда с собственным хранилищем, API и публикуемыми событиями.
- Контракты фиксируются в Schema Registry, а не в общей БД.
- Data Product Owner в каждом домене отвечает за качество и доступность данных.

Преимущества: параллельная разработка в нескольких доменах без блокировок.

### 3.5. Отказоустойчивость и надёжность

Проблема: сбой Apache Camel или DWH парализует все системы.

Решение с EDA:
- Брокер событий (Kafka) хранит события на диске с настраиваемым retention.
- При сбое потребителя события накапливаются и обрабатываются после восстановления (replay).
- DLQ (Dead Letter Queue) для обработки ошибок без потери данных.
- Каждый домен это отдельный failure domain.

Преимущества: система продолжает работать даже при частичных сбоях.

### 3.6. Регуляторное соответствие и аудит

Проблема: работа с медицинскими данными (ФЗ-152, стандарты Минздрава) и финансовыми данными (ЦБ РФ, PCI DSS) требует строгого аудита.

Решение с EDA:
- Event log = неизменяемая история всех действий (кто, что, когда).
- Разделение PHI (Protected Health Information): медицинские данные не покидают клинический домен; в события включаются только метаданные.
- Consent-driven обработка: ConsentRevoked -> все подписчики прекращают обработку данных пациента.

Преимущества: встроенное соответствие регуляторным требованиям.

## 4. Сравнение с альтернативами

### 4.1. Почему не модернизация Camel

| Аргумент                                   | Контраргумент                                                                                                                                    |
|--------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| "Просто обновим Camel до последней версии" | Camel - это middleware для маршрутизации, не event broker. Он не обеспечивает: retention, replay, horizontal scaling consumers, schema evolution |
| "Добавим новые маршруты для новых доменов" | Количество point-to-point маршрутов растёт квадратично: N доменов -> N*(N-1)/2 маршрутов. При 7+ доменах это неуправляемо                        |
| "Camel поддерживает async через JMS"       | JMS-очереди не дают publish-subscribe семантику "один-ко-многим", критичную для Data Mesh и Analytics                                            |

Вывод: Camel сохраняется на этапе миграции как «мост совместимости» через Anti-Corruption Layer, но не является целевым решением.

### 4.2. Почему не замена DWH на современный (Snowflake, BigQuery)

| Аргумент                        | Контраргумент                                                                                                                   |
|---------------------------------|---------------------------------------------------------------------------------------------------------------------------------|
| "Просто мигрируем DWH в облако" | Это решает проблему производительности, но не решает проблему связанности: бизнес-логика по-прежнему в одном месте              |
| "Новый DWH быстрее"             | Быстрее, но архитектура остаётся batch-ориентированной (пусть и с streaming ingestion). Не решает задачу near-real-time реакции |
| "Все данные в одном месте"      | Нарушает принцип доменной автономии; мешает масштабированию команд                                                              |

Вывод: облачный DWH / Data Lake используется как один из компонентов аналитического домена (для сложной ad-hoc аналитики), но не как центральный интеграционный хаб.

## 5. Стратегия миграции (Strangler Fig Pattern)

Переход от текущей архитектуры к EDA реализуется поэтапно через паттерн Strangler Fig:

### Этап 1 (0–6 месяцев): пилот
- Развернуть Kafka-кластер в облаке.
- Выбрать 1–2 домена для пилота (рекомендация: FinTech + Billing - чёткие границы, высокая бизнес-ценность near-real-time).
- Создать ACL-адаптеры: Camel -> Kafka, DWH CDC -> Kafka.
- Определить каталог схем и стандарты событий (Schema Registry).
- Внедрить DLQ и базовый мониторинг.

### Этап 2 (6–18 месяцев): расширение
- Подключить Clinical, AI Services и Patient домены.
- Запустить потоковые витрины данных (Kafka Streams -> ClickHouse -> BI).
- Вывести портал самообслуживания (Data Showcase) на основе материализованных представлений.
- Начать дублирование критических маршрутов Camel через Kafka (dual write).

### Этап 3 (18–36 месяцев): полный переход
- Отключить синхронные Camel-маршруты на критическом пути.
- Перевести DWH в режим "архивное хранилище" (read-only).
- Запустить доменную аналитику на основе потоков (каждый домен публикует свои data products).
- Подключить новые бизнес-направления (фармакология, электроника) нативно через EDA.

## 6. Риски событийного подхода и их митигация

| Риск                                                                    | Вероятность | Митигация                                                                                                |
|-------------------------------------------------------------------------|-------------|----------------------------------------------------------------------------------------------------------|
| Eventual consistency: временная несогласованность данных между доменами | Средняя     | Saga-паттерн для критических процессов (кредитование); idempotency keys; мониторинг lag                  |
| Операционная сложность Kafka: требуется экспертиза                      | Средняя     | Managed Kafka (Confluent Cloud / Yandex MKF); обучение команды; SRE-практики                             |
| Дублирование данных: каждый домен хранит свою проекцию                  | Низкая      | Это intentional tradeoff; single source of truth = event log; CQRS для актуальных проекций               |
| Порядок событий: нарушение ordering при масштабировании                 | Средняя     | Партиционирование по aggregate ID; sequence numbers; при необходимости: single partition per aggregate   |
| Сложность отладки: распределённые потоки сложнее трассировать           | Средняя     | Correlation ID + Causation ID в каждом событии; distributed tracing (Jaeger/Zipkin); centralized logging |
| Миграция legacy-данных: перенос исторических данных из DWH              | Высокая     | CDC (Debezium) для snapshot + ongoing changes; ACL для трансформации; поэтапный подход                   |

## 7. Заключение

Событийный подход (EDA) для "Будущего 2.0" не просто замена технологии интеграции, а фундаментальный переход к архитектуре, которая:

1. Соответствует бизнес-стратегии: масштабирование по продуктам, географии и данным.
2. Устраняет системный bottleneck: DWH перестаёт быть единственной точкой интеграции и отказа.
3. Обеспечивает автономию: каждый домен (клиники, ИИ, финтех) развивается независимо.
4. Повышает скорость реакции: от batch-отчётов за часы к near-real-time обработке за секунды.
5. Упрощает подключение новых направлений: фармакология и электроника подключаются как новые подписчики без рефакторинга существующих систем.
6. Строит основу для Data Mesh: события = data contracts между доменами; каждый домен предоставляет данные как продукт.

Текущие Apache Camel и DWH сохраняются на этапе миграции как "мосты совместимости" через Anti-Corruption Layer, но целевое состояние это полностью событийная платформа с доменной аналитикой.
